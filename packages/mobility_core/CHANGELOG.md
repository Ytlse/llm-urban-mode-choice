# Changelog — mobility-core

Format: `## [version] - YYYY-MM-DD`, most recent entries first. The tone is that of use. The
files touched are in git.

## [Unreleased]

**Declared licence** (ticket 038): `Apache-2.0` for the code, plus a `NOTICE` stating that
this licence **does not cover** the resources in `data/` — derived from the EMC² Toulouse 2023
survey, ProGEDO / ADISP agreement lil-1750, research use and citation of the survey.

**The package no longer ships restricted-access resources.** `package-data` lists its eight
resources one by one instead of a `data/*.json` glob, `include-package-data` is set to
`false` — at `true` it merges with the list instead of restricting it — and a whitelist
`MANIFEST.in` governs the sdist, which `pyproject.toml` does not reach. Removed from both
archives: `zf_couronne.json` (sampling plan), `zf_housing_type.json` (counts per fine
zone), `zf_zones.gpkg`, `zf_zones.meta.json`. `tests/test_packaging_licence.py` builds the
sdist and wheel and checks their content — the declaration is not authoritative, the artifact is.

**New entry point `resources.restricted_data_path(nom)`**, with
`restricted_data_candidates`, `restricted_resource_hint` and the `RESTRICTED_RESOURCES` table.
Search order: `$MOBILITY_CORE_EMC2_DATA_DIR`, the package's `data/`, then a plausible
repository root. `residence_zone`, `housing_type` and `zone_resolver` use it; when not found,
they raise, naming the resource, the `make` command, the variable and the paths tried.

No effect at run time: the containers mount `src/mobility_core/` and the venv is an
editable install. A `pip install mobility-core` no longer has `zf_couronne.json` —
`CouronneTable.load()` then says so explicitly.

## [0.1.0] - 2026-09-07

First installable version of the EMC² Toulouse survey domain, extracted from
`llm_module.core` (ticket 037). The package depends on no LLM and no infrastructure: no
`llm_gateway`, Redis, Celery, httpx, FastAPI or Jinja2 (import-linter contract
`domaine-sans-gateway`).

**What the package provides, to those who use it:**

- **Residence rings** read from a list of communes (`residence_zone`), **fine zones**
  and geographic variables of mode choice (`zone_resolver`, extra `geo`), **hypercentre**
  read from the feature contract and never redeclared (`geo_reference`).
- **Mode hierarchy** of the survey (`mode_hierarchy`): a multimodal trip receives a main
  mode, the same across the whole repository.
- **Imputed equipment and housing, deterministic by hashing**: bike in three stages
  (`bike_ownership`), PT pass and driving licence (`equipment_propensity`), housing type
  conditioned on the zone and on household size (`housing_type`).
- **Framing of the surveyed population** (`population_reference`): scope, rings,
  household targets, `household_weight` weighting.

**Before:** these modules climbed two levels up to the repository root and read
`/app/scripts/...` hard-coded to find `feature_spec.json` or `population_emc2_2023.yaml`.
**After:** `mobility_core.resources.find_repo_file` searches, in order, the dedicated
environment variable (`MODE_CHOICE_FEATURE_SPEC`, `POPULATION_EMC2_REFERENCE`), the
`MOBILITY_CORE_REPO_ROOT` root, a walk up from the current directory, then `/app`. The
frozen survey resources ship in `mobility_core/data/`; those derived from restricted-access
microdata (`zf_zones.gpkg`, `zf_zones.meta.json`, `zf_housing_type.json`) stay out of git
and are regenerated by `make zones` and `make housing-type`.

Tests: 199 collected on 2026-09-07 (1 skipped without the zone layer), `needs_data`
marker declared for tests that require a resource produced outside git.
